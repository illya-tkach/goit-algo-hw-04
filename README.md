## Завдання 1 — `task1_sort_files.py`
Рекурсивне копіювання файлів із сортуванням у піддиректорії за розширенням.

- **Аргументи:** `source` (вихідна директорія) та необов'язковий `destination` (за замовчуванням `dist`), парсинг через `argparse`.
- **Рекурсія:** `process_directory(path, destination)` перебирає всі елементи директорії; для піддиректорії викликає себе рекурсивно, файл передає в `copy_file`.
- **Копіювання:** `copy_file` створює піддиректорію з назвою розширення (`txt`, `png`, …; файли без розширення потрапляють у `no_extension`) і копіює туди файл через `shutil.copy2`. Файли з однаковими назвами не перезаписуються, а отримують суфікс `_1`, `_2`, …
- **Винятки:** обробляються `PermissionError` та `OSError` для директорій і файлів, тож недоступні елементи пропускаються з повідомленням, а не зупиняють програму. Неіснуюча вихідна директорія дає зрозумілу помилку.

```bash
python3 task1_sort_files.py ./source            # результат у ./dist
python3 task1_sort_files.py ./source ./sorted   # власна директорія призначення
```

## Завдання 3 — `task3_sorting_comparison.py`
Порівняння сортування злиттям (merge sort), вставками (insertion sort) та Timsort (вбудований `sorted`). Час вимірюється модулем `timeit` (найкращий результат із 3 повторів) на чотирьох наборах даних: випадковий, відсортований, зворотно відсортований та майже відсортований (≈1% переставлених елементів).

```bash
python3 task3_sorting_comparison.py
```

### Перевірка теоретичних оцінок

- **Insertion sort — O(n²) у середньому та найгіршому випадку, O(n) у найкращому.** При збільшенні n удвічі (5 000 → 10 000) час на випадкових даних зростає ≈ в 4 рази (0.36 → 1.44 с), на зворотних — теж ≈ в 4 рази (0.71 → 2.95 с). Зворотний масив — найгірший випадок, удвічі повільніший за випадковий. На відсортованих даних час росте лінійно (×2) — це найкращий випадок O(n), і тут вставки швидші за злиття.
- **Merge sort — O(n log n) завжди.** При збільшенні n у 10 разів (10 000 → 100 000) час зростає ≈ в 12 разів (0.0156 → 0.192 с), що відповідає n log n (10 × log(10⁵)/log(10⁴) ≈ 12.5). Час майже не залежить від впорядкованості даних — алгоритм не використовує наявний порядок.
- **Timsort — O(n log n) у найгіршому, O(n) у найкращому випадку.** На випадкових даних росте як n log n (×13 при 10 000 → 100 000), а на відсортованих і зворотних — лінійно (×11–12), бо Timsort знаходить готові впорядковані ділянки (runs) і лише розвертає спадні.

### Висновки

1. **Timsort найшвидший на всіх наборах даних.** На випадкових даних він у ~18 разів швидший за наш merge sort і в ~1 700 разів швидший за insertion sort (n = 10 000); на відсортованих і зворотних — у сотні разів швидший за merge sort.
2. **Чому поєднання злиття і вставок працює:** Timsort ділить масив на природні впорядковані ділянки (runs), короткі ділянки добудовує сортуванням вставками (яке на малих і майже впорядкованих фрагментах дуже швидке — див. рядки n = 100 та «майже відсортований»), а потім зливає їх як merge sort. Так він бере лінійну поведінку вставок на впорядкованих даних і гарантію O(n log n) від злиття, уникаючи квадратичного найгіршого випадку вставок і зайвої роботи злиття на вже впорядкованих даних.
3. **Додатковий виграш — реалізація на C**, тоді як наші версії написані на чистому Python. Навіть для однакової асимптотики (O(n log n) на випадкових даних) вбудований `sorted` швидший більш ніж на порядок.
4. **Тому на практиці** варто використовувати вбудовані `sorted()` / `list.sort()`: вони швидші, стабільні, адаптивні до реальних (часто частково впорядкованих) даних і вже налагоджені. Власні реалізації сортування мають сенс лише для навчання або дуже специфічних задач.
